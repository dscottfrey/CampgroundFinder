## The rules that were learned the hard way

These cost hours. Do not rediscover them.

### Silently short results are this project's recurring bug

Six separate instances today, all the same shape: **a wrong answer that looks
like a complete one.**

| where | what happened |
|---|---|
| ReserveAmerica directory | half its responses truncate mid-`<head>`; a cut-off page parses to zero rows and read as "end of directory" — stopped at 25 of 65 parks |
| ReserveAmerica matrix | RA appended `&lengthOfStay=1`; the pattern stopped matching and **every Oregon park read "full"** |
| ReserveAmerica site list | `campgroundDetails.do` ignores `startIdx`; Beverly Beach looked like 27 sites, has 279 |
| BC Parks API | Strapi ignores `offset`, and unsorted paging returned 1052 rows holding 736 distinct parks |
| RIDB campsites | `campsites?facilityID=X` as a query param is ignored, returning all 137,117 campsites |
| scanner | one source's failure marked all 545 campgrounds on that provider stale, including one with 556 openings |

**The habit that catches them: check every result against the source's own
stated total, and never accept a zero that the page contradicts.** Every walk
in the codebase now does this and raises rather than returning short.

### Data quality belongs to the campground, not the provider

Do not say "federal data is good". Two RecreationDotGov campgrounds land on
opposite verdicts. `equipment.grade_lengths()` judges each campground from its
own spread of values.

### The driveway length is a floor, not a measurement

A Beverly Beach manager told Scott they had no staffing to measure when going
onto ReserveAmerica, so most sites got a default — 21 of 24 read "20 Back-In".
A01 lists 20 and is really 53 feet; A15, genuinely short, was entered
accurately at 15.

**Scott's tell:** no real campground has most sites the exact same length. A
repeated value is a form default and means nothing; a rare value was entered
deliberately and should be believed.

**And never show "minimum 20 ft" to a 40-foot rig.** `filter_by_length()`
returns three buckets — fits / unknown / no — so unknowns are never presented
as matches.

### Never let a filter exclude on data that can't support it

* `TENT SITE` is **not** an equipment restriction. Scott has camped Beverly
  Beach C27 in a van. Only an explicit "RV prohibited" in the site description
  says otherwise, and we don't read descriptions.
* The ReserveAmerica type **icon** is wrong — all 21 `WALK TO` sites at Stub
  Stewart carry an `rv` icon and cannot take an RV.
* First-come campgrounds must never read "full". They have no feed; an empty
  result says nothing.

### Vocabulary

**Never say "walk-up"** — half the world reads it as access ("carry your
gear"), half as booking ("turn up without a reservation"). Say "first-come,
first-served" for booking and "hike-in" for access. They are independent axes.
See `docs/terminology.md`.

### Stop chasing anomalies

Scott's call, and right. The anomaly work paid for itself several times, but it
has a floor: A19 at Beverly Beach looked like a camp host pitch from three
converging signals, and turned out to book normally. Report anomalies; don't
guess their cause.

## The question this all has to answer

Scott, 2026-07-31 — the acceptance test for the whole interface:

> "It's Wednesday, where can I camp this weekend where there is a lake, where
> the daytime high is at least 80 but less than 95, and the forecast is not
> for rain or clouds or > yellow AQI"

Four things that pins down, each of which changes a decision already on the
list below:

* **This is an app for impulse trips, not for a summer holiday planned in
  January.** Scott's framing, and it settles more than it looks: the date
  control is a **dropdown**, not a calendar — *tonight · tomorrow · this
  coming weekend · pick a start date* — beside a second dropdown for
  **1, 2 or 3 nights**. (`config.yaml` currently sets `nights_options:
  [2, 3, 4]`; that wants to become 1–3.)
* **So the forecast horizon stops being a limitation.** An impulse trip is
  always inside the ~7–10 day forecast window, which is precisely where the
  weather filters work. Only the "pick a start date" branch can fall outside
  it, and there the filters go quiet — `unknown` dims, it never hides.
* **AQI needs a category, not a boolean.** The planned
  `aqi_status` of `green` / `not_green` **cannot express this** — yellow is
  acceptable to him. Store the real category.
* **The temperature filter has two bounds**, and the forecast filter covers
  precipitation *and* cloud cover, not just rain.
* **"Near water" is a good enough flag for "a lake".** Scott, same day, heading
  off a rabbit hole: don't build a curated lake/river/ocean distinction yet.
  ReserveAmerica states `Near Water` per site and that will do.

## What's next

**The map.** There are now 35,000 real openings and no way to look at them.
`manage.py demo` serves a list only. Everything built for honesty — stale,
unknown, first-come, unlocated, the length caveats — is display logic with
nowhere to display. Steps 4 and 5 of the scanning design (on-demand refresh,
zoom priority) also can't start without one.

After that, in rough order:

* **Re-lay-out the map page: full-bleed map, floating chrome.** The map is a
  window today, below four stacked rows of header, controls, base-map buttons,
  and legend. Make the map the page; collapse search, filters, and the view
  switcher into one top bar; float zoom, locate, legend, and share in the
  corners; put pill-shaped backgrounds behind the campground labels. Light
  surfaces, not black slabs. Spec and reasoning in
  [`campsage-ui-notes.md`](campsage-ui-notes.md) — "Map chrome".
* **Provider coverage, in the order settled with Scott on 2026-07-31.** Depth
  where he camps beats breadth:
  1. **GoingToCamp per-site inventory** — Washington's 79 parks and BC's 114
     have *zero* site-level data, so the equipment and hike-in filters are
     blind in a state he actually camps in. Same job just finished for
     Oregon, one provider over; `inventory._source_for` refuses GoingToCamp
     today by design.
  2. **CampLife / PacifiCorp** — a large number of highly desired Washington
     sites. Blocked on inspecting the booking network calls; see §3b of
     `campgroundfinder-subdirective-county-municipal.md`.
  3. **Parks Canada** — `reservation.pc.gc.ca`, GoingToCamp rec area **14**.
     The build plan's claim that it needs a custom provider is wrong; it is a
     host-table entry and a config line. Free breadth once the depth is done.
  4. **County/municipal portals** — inspect first, build second. Several may
     land on platforms we already have.
  5. **OregonMetro** — implemented already, but Scott rates it far less
     desirable. Bottom of the list deliberately.
* **AQI, and sooner than planned.** Scott, 2026-07-31: *"most of eastern
  Washington and Oregon is on fire and blanketed with smoke."* The scan that
  day found 38 sites free at Yakima Sportsman and 148 openings across the
  park — verified real, not a parsing bug. **They are free because the air is
  unbreathable.** Which makes air quality not an enhancement but a
  correctness problem: without it the map's most confident answers point at
  exactly the places nobody should go, and "lots of availability" reads as
  good news when it is the opposite.

  **It is two features, not one**, and Scott's AirNow screenshot is the
  argument for the second:

  1. **A value per campground**, driving the filter in his canonical question
     ("no worse than yellow"). `air-quality-api.open-meteo.com` is already on
     the network allowlist, takes a lat/lon, and needs no key. The stored
     value must carry the **real category** — the planned
     `green` / `not_green` cannot express "yellow is fine".
  2. **A shaded layer over the map**, like
     [AirNow's interactive map](https://fire.airnow.gov). A number in a popup
     tells you about one campground; the contours tell you *the whole east
     side is out* at a glance, which is the actual decision. Note the
     parks.wa.gov alerts page links to AirNow itself — the operator points
     campers there.

  Unverified, to check before building the layer: AirNow's map is Esri/ArcGIS
  powered, so the NowCast contours are probably a feature or tile service we
  could consume directly; their own API (airnowapi.org) needs a free key,
  which is Scott's call since it means signing up. Data refreshes hourly, so
  this is a periodic job, not a per-request fetch.

  **Why both, and in that order** (Scott's point, 2026-07-31): a campground
  ruled out by the AQI filter dims to 35%. **Dimming says "ruled out"; it does
  not say why.** Put the shaded layer underneath and a faded dot sitting
  inside an orange contour answers the question spatially, instantly, with
  nothing to read. The layer is what makes the dimming legible — they are not
  two parallel features, the second completes the first.

  **Never derive the pin's value from the layer.** Scott, same conversation:
  *"a campsite in a pocket valley might be good, yet inside that layer — so
  it would be more apparent."* The contours are interpolated from a sparse
  monitor network, and in mountainous country the interpolation is weakest
  exactly where the terrain matters most. A sheltered valley can hold clean
  air inside a region shaded orange.

  So the two must be able to **disagree**, which means the pin's value comes
  from point data (open-meteo's forecast for that lat/lon, or the nearest
  monitor) and never from sampling the contour. The disagreement is then the
  most useful thing on the screen: **an undimmed pin sitting inside an orange
  field is a candidate**, and it is visible precisely because everything
  around it is not. A system that derived the dot from the layer could never
  show that — it would paint the valley orange and hide the answer.

  The converse is a warning sign worth watching for: a dimmed pin in a clean
  field usually means the point data is stale or the coordinate is wrong.

  **A 13px dot at 35% over a saturated contour may vanish outright** — small
  area, low opacity, loud background, the combination Scott warned about.

  **Do not pre-solve this.** His answer when it was raised: *"correct, and I
  may want that, and I will not know until I see it live."* A campground
  ruled out by air quality dissolving into the smoke that ruled it out may be
  exactly right — the map would be showing the reason rather than fighting
  it. So build the plain version, put it on screen, and let him look
  ([[build-visual-things-dont-reason-about-them]]). Nobody should be
  designing outline-at-full-opacity workarounds for a page that does not
  exist yet.

  **Colour caution:** AirNow's own scale is green/yellow/orange/red/purple —
  the classic confusion set, and unusable as-is
  ([[scott-is-colorblind]]). If we render our own contours the categories
  need lightness separation or hatching, not their palette. Their tiles, if
  used as-is, at least carry a legend Scott can check against.
* **Filters dim, they never hide.** Every campground keeps a dot at every
  zoom and under every filter — density and navigation come free from that,
  and hiding is the CampSage behaviour Scott most dislikes. Non-matching
  campgrounds drop to ~50% opacity (dot *and* name tag), triggered by no
  availability in range, AQI, temperature, forecast, or a missing amenity.
  **Not cumulative** — failing four filters looks like failing one. Names
  stay hidden until higher zooms; the dot matters, the name mostly doesn't.
  Detail in [`campsage-ui-notes.md`](campsage-ui-notes.md).
* **Campfire bans — Washington is solved, the rest isn't.** Scott found
  `parks.wa.gov/about/news-announcements/alerts` on 2026-07-31: every state
  park's burn ban level, dated, in **server-rendered HTML on one page**. One
  request a day covers Washington. The same page also carries **park closures**
  — which should feed catalog status, and is a bigger honesty win than the
  fire filter itself, since today we would show a closed park as `unknown` and
  let somebody drive there. Needs `parks.wa.gov` on the allowlist. Detail and
  caveats in [`fire-restrictions.md`](fire-restrictions.md). Oregon, the
  national forests and BC are still unresearched.
* **Per-user preferences, stored on the account.** Since there's a login
  anyway, theme (light/dark/auto), which filter chips a user wants in the bar,
  their defaults, and "remember how I set them" should live in the `users` row
  rather than in cookies. The role model is already designed — `users.role` is
  `'admin' | 'friend'` with an approval `status` — so this is one `prefs` JSON
  column plus a settings page. Detail in
  [`user-preferences.md`](user-preferences.md).
* **Inventory drift detection, with an admin view.** When a scan returns a
  `site_id` the `campsites` table doesn't know, that's the inventory telling
  us it's stale — a free signal at no extra request cost. Settled with Scott
  2026-07-31, the handling is:
  * **Never auto-correct.** An availability response carries a site id and
    maybe a name, not loop / site type / driveway / access class. Writing
    that as inventory creates a stub that reads as measured — the A19
    failure shape.
  * **Never trigger a full rescan.** One unknown id must not cause hundreds
    of upstream requests; §6c says user activity changes what and when,
    never how fast.
  * **Queue a park-level inventory refresh**, run by the scanner at its
    normal pace. One page walk, self-checked against the park's own "N
    site(s) found".
  * **Alert the admin on confirmed drift**, not on the raw sighting — an
    unknown id may be a transient or a mis-parse, and alerting on those
    trains the admin to ignore the alert.
  * Needs its own small table; `scan_status` is a singleton progress row.
    `campsites.source` / `.updated` already carry provenance.
* **Wire the equipment filter into availability.** `app/equipment.py` works and
  is tested, but nothing joins it to search results yet. The `campsites` table
  joins to `availability` on campsite id — that's the missing piece.
* **Scanning design step 3** — background sweep with adaptive cadence. Note its
  trigger is "someone active in the last 15 minutes", which needs a UI to exist.
* **Enrichers** (build plan step 4) — AQI, wildfire, water, weather.

## Open questions to discuss — not researched yet

* **Push the on-demand availability queries into the client browser?** (Scott,
  2026-07-29.) Today every provider request comes from one home IP, so the
  traffic all looks like one machine polling. If the live "is this site free
  right now" query ran as fetches from each visitor's own browser, the load
  would be spread across ~12 residential IPs and would look like twelve people
  each checking a campground — which is what it actually is. Server-side
  scanning would still be needed for the notification watches, so this is a
  split, not a replacement. Unknowns to settle before building anything: CORS
  and whether each provider's endpoints are callable from a browser at all,
  whether API keys can stay out of client code, how results get back into our
  cache and honesty stamps, and whether this is consistent with
  [[campgroundfinder-scraping-policy]] — the rule is "don't get banned", and
  it's an open question whether distributing requests reads as considerate or
  as evasion.

## The water/beach/boat flags don't exist where we assumed (2026-07-31)

Scott's reasonable guess was that "near water", "beach" and "boat launch" are
probably standard flags. Measured against all 64 backfilled Oregon parks and
5,413 sites, they are not:

* **`Near Water` exists and is `no` on all 5,313 sites that carry it.** Zero
  `yes`, including Beverly Beach, South Beach and Cape Lookout, which are on
  the ocean. Oregon State Parks never filled the field in. A filter built on
  it would return nothing, forever — the silently-short shape again, so it
  must not be built on this.
* **There is no beach or boat-launch flag at all** in ReserveAmerica's
  per-site table. The columns are Site#, Loop, Site type, Max people,
  Equip length/Driveway, Amenities, Online availability, and the Amenities
  icons only ever say: Pets Allowed, Electric Hookup, Full Hookup, Water
  Hookup, Near Water, Accessible site.

**Where to look next, unverified:** these are *park*-level facts, not per-site
ones, and we only parse the site table. RA's park page carries a description
and facility list we don't fetch; RIDB has facility-level attributes and
activities for the federal side. That is the next thing to check before the
amenity filter in [`campsage-ui-notes.md`](campsage-ui-notes.md) can work —
and it may end up as another field we curate ourselves, like the photos.

## Missing campgrounds — the completeness floor is leaking (2026-07-31)

Scott: **"Heart O' The Hills campground in Olympic National Park is missing
entirely."** Checked: Kalaloch is in the catalog; Heart O' The Hills, Hoh and
Sol Duc are not. **Olympic is partially present, which is worse than absent** —
the map looks like it covers the park, so nobody thinks to doubt it. That is
precisely the failure §8k exists to prevent.

Most likely cause, unverified: those are **first-come campgrounds**, and RIDB's
facility enumeration is driven by the reservation system, so a campground that
takes no bookings was never loaded into it (`app/inventory.py` already
documents 206 of 803 facilities returning zero campsites for this reason). If
so, the gap is systematic and quiet — every first-come campground in the
region is likely missing, which is exactly the camper this project set out to
serve.

**Scott notes it is also missing from CampSage**, which is strong
confirmation rather than mere company: their catalog is built on the
reservation systems too, so a campground that takes no bookings is invisible
to them *by construction*. Two independent products with the same hole point
at the same cause.

It is also the clearest differentiator yet. Showing first-come campgrounds is
something CampSage structurally cannot do, and it is exactly the camper this
project set out to serve — the one driving out on a Friday without a booking.
Worth adding to the acceptance test that already pins the campgrounds
CampSage misses.

**Two `state`-tagged North Dakota grasslands** come from the same area of the
code: enumeration stamps the *source's* configured state onto every facility
instead of reading the facility's own `AddressStateCode`. Little Missouri and
Sheyenne National Grasslands are both filed under WA.

**And `rec_area` holds the wrong thing entirely.** Every RecreationDotGov row
reads "Campground", "Facility" or "Permit" — the facility *type*, not the
recreation area. So there is no way to ask for "Olympic National Park", and
the popup's location line says nothing useful.

## Known problems, none blocking

* ~~**Gifford Pinchot's rec-area id `1131` is wrong**~~ — **fixed 2026-07-31.**
  The real id is **1117**. `1131` is *Foss Reservoir*: a real rec area, the
  wrong one, with zero facilities — which is why it failed as "No campgrounds
  found to search" rather than as a 404. Exactly the
  [[build-plan-data-is-made-up]] pattern: a plausible number that points
  somewhere real and wrong. Corrected in `config.yaml` and
  `config.example.yaml`; the build plan's §12 sample still says 1131.
* **ReserveAmerica site inventory is not stored.** `list_sites()` now walks
  every page correctly, but nothing calls it during a scan, so the `campsites`
  table holds federal sites only. Oregon's per-site data (including the
  `WALK TO` access signal) is one backfill away.
* **camply's internal pacing is unverified.** It owns its own HTTP and fires
  several requests per search; the adapter holds the shared slot around the
  whole call, which stops our other providers piling on but doesn't pace
  camply's own bursts.
* **The rate limiter is per-process.** Two processes hitting the same host
  don't coordinate. Fine today; matters when the web UI can trigger scans.
* **A rec-area-scoped source can't stamp its campgrounds full.** `Campground`
  doesn't record which rec area it belongs to, so we can only stamp what came
  back. Capturing `rec_area_id` during enumeration would fix it.

* `config.yaml` exists now (gitignored), created from the example. It enables
  Oregon and Washington state parks plus three national forests.
